전략기술 분야별 논문성과 분석 서비스

OpenAlex · KCI에서 전략기술 분야별 한국 논문을 검색하고, abstract 기반으로 주요 기술적 성과를 종합 정리해 마크다운/PDF 보고서로 출력하는 서비스.
레퍼런스: references/17_Spec-investigation (TechSpec) — 검색 에이전트·Gemini 호출·Docker 구성 재활용.

항목결정
분야 정의12대 국가전략기술 프리셋을 seed로 넣고, 하위 세부기술 단위까지 관리자가 관리

(연도간 변화·부상 키워드는 이번 범위에서 제외)

논문 1건 성과 추출은 추론 부담이 낮음. 전 단계 high 대비 비용 3~5배 절감

핵심 선택지 — 논문 N건 → 분야 보고서

추천 · 채택안

A. 논문단위 map → 분야단위 reduce

  • map: 논문 1건 = Batch 요청 1개. title + abstract → {세부기술 태그, 기술적 성과 요약 1~2문장, 성과유형(신소자/공정/알고리즘/성능향상…), 정량수치} 구조화 추출
  • reduce: 분야별로 map 결과(논문당 ~50토큰)를 한 번에 투입해 보고서 서술 + 클러스터링 (동기 1~2콜)
  • 캐시가 논문 단위라 재분석·당해연도 갱신 시 신규 논문만 과금. 근거 논문 역추적 가능

B. 청크 요약 (30건씩 묶어 요약 → 요약 합성)

호출 수 1/30로 가장 저렴. 그러나 캐시 단위가 청크라 논문 1건만 늘어도 청크 전체 재호출 — "동일 내용 검색 시 API 재호출 금지" 요구와 충돌. 근거 추적도 흐려짐.

C. abstract 전량을 1콜에 투입

구현 최단. 수천 건이면 컨텍스트 초과 + 누락·환각 위험, 캐시 불가.

결론: A 채택. Batch API 50% 할인과 논문단위 캐시가 맞물려야 재호출 방지 요구가 실제로 성립.

규모 검증 — 한 세부기술에 논문 3,000건인 경우

단계3,000건 기준
사전 필터DOI/title 중복 제거 · 한국 소속 필터 · 추출 캐시 히트 제외 → 실제 LLM 대상은 그보다 작음. 재실행 시엔 신규분만
map 요청3,000개 → JSONL 파일 업로드, 1,000건 단위 분할 제출
map 토큰입력 ~700/건 = 2.1M · 출력 ~250/건(thinking low) = 0.75M
map 비용Flash-Lite batch 기준 대략 $0.2~0.4 (추정 · 구현 시 실단가 확인)
소요보통 수십 분, 상한 24h

병목은 map이 아니라 reduce. 3,000건 요약을 한 콜에 넣으면 ~180K 토큰이라 컨텍스트에는 들어가도 종합 품질이 떨어짐. 계층 구조가 이를 자연히 해소:

세부기술 A (300건) → reduce 1콜 (~18K)  ┐
세부기술 B (250건) → reduce 1콜         ├→ 대분류 합성 1콜 (~20K)
   … 세부기술 10개                      ┘

한 세부기술이 500건을 넘으면 성과유형/클러스터별 그룹 요약을 끼워 3단 reduce로 자동 분기.

실행 전 관리자 화면에 예상 규모·비용을 먼저 표시하고 확정을 받음 (검색만 선행 → “신규 1,240건, 예상 $0.4, 실행?”).

Rate limit 제어

Batch와 동기 호출은 제한 체계가 다르므로 경로를 분리해 다룬다.

경로실제 걸리는 제한대응
Batch 제출 (map)RPM 아님 — 모델별 enqueued token 총량, 동시 batch job 수, 입력 파일 2GB제출 전 토큰 합산 → 슬롯 게이트
동기 호출 (reduce)RPM · TPM토큰버킷 2종 + 429 지수 백오프
검색 APIOpenAlex polite pool ~10 req/s · KCI 동시성 3asyncio.Semaphore

사전 체크 (pre-flight)

  • 제출 대상 논문 리스트로 예상 입력 토큰을 먼저 합산. 추정식은 문자수 / 4 — count_tokens API를 논문마다 부르면 그 자체가 호출 낭비. 게이트 판단엔 ±20% 오차로 충분
  • 진행 중 batch job의 enqueued 토큰 합 + 신규 예상치가 한도 이내일 때만 제출. 초과하면 대기 큐에 두고 백그라운드 루프가 슬롯이 비는 대로 순차 제출
  • 파일당 요청 수 상한(BATCH_MAX_REQUESTS_PER_FILE, 기본 1,000)으로 분할
  • 관리자 실행 확정 화면에 예상 토큰·비용·제출 청크 수를 함께 표시

런타임 방어 (사전 체크만으로는 부족)

동일 프로젝트 쿼터를 다른 분야 작업·타 서비스가 함께 소비하므로 429는 어차피 발생한다. 게이트와 재시도를 둘 다 둔다.

  • 429 / RESOURCE_EXHAUSTED → 지수 백오프(1·2·4·8·16초, 최대 5회), Retry-After 헤더 우선
  • 동기 호출은 RPM·TPM 두 개의 토큰버킷을 모두 통과해야 발사
  • 재시도 소진 시 해당 청크만 failed 표시 후 계속 진행 — 전체 잡을 죽이지 않음. 관리자 화면에서 실패분만 재실행

한도값은 모델·티어별로 달라지므로 전부 .env: BATCH_MAX_ENQUEUED_TOKENS, BATCH_MAX_CONCURRENT_JOBS, BATCH_MAX_REQUESTS_PER_FILE, SYNC_RPM, SYNC_TPM. 코드에 하드코딩하지 않는다.

연도 처리 — 프리즈 없음 (전량 증분 갱신)

과거연도 freeze는 폐기. 전년도 논문이 올해 새로 포착되는 경로가 여러 개이기 때문:

요소영향
색인 지연KCI 발행 후 3~6개월, OpenAlex는 Crossref 경유로 수주~수개월. 2025-12 발행 논문이 2026-03에야 검색됨
online-first 연도 재배정선공개 후 정식 호 게재 시 publication_year가 사후 변경
메타데이터 사후 보정저자 소속(=한국 판정 근거)·abstract가 나중에 채워짐. 최초엔 제외됐던 논문이 이후 KR로 확정
검색식 변경관리자가 검색식을 고치면 과거연도 보고서도 stale. 프리즈면 낡은 결과가 그대로 남음
인용수계속 증가하는 값 → “언제 기준”인지 명시 필요
  • 모든 연도가 증분 재실행 대상. 캐시가 논문 단위라 재실행 비용은 신규분에만 발생 — 프리즈로 얻는 이득이 거의 없음
  • analyses에 snapshot_at(최종 수집 시점)과 query_hash 기록. 검색식이 바뀌면 해시 불일치로 해당 연도가 자동 “갱신 필요” 표시
  • 관리자 화면에 연도별 최종수집일 / 논문수 / 상태(최신·갱신필요)를 노출, 실행 대상 연도를 체크해 실행
  • 기본 실행 범위는 최근 3개년으로 제한해 습관적 전량 재실행 방지
  • 인용수 통계에는 snapshot_at 기준임을 보고서에 명시
  • 분야(대분류) 보고서: 하위 세부기술 보고서들을 상위 합성 1콜로 결합
1/2 확정 사항
  • ✅ A안(map→reduce) 채택 · map thinking low / reduce thinking high
  • ✅ 검색식은 세부기술(중점기술)에만 보유 — 대분류는 하위 합성만 담당
  • ✅ 과거연도 프리즈 폐기 → snapshot_at + query_hash 기반 증분 갱신
  • ✅ Rate limit — 제출 전 토큰 게이트 + 429 백오프 병행, 한도값은 전부 .env

잡 상태 머신 · 재시작 안전성

pending → searching → extracting → reducing → done
                          │            │
                          └──→ failed ←┘   (실패 청크만 격리, 부분 재실행 가능)

Batch는 최대 24h이므로 컨테이너 재시작이 반드시 걸린다. 진행 상태·batch job id를 전부 DB에 두고, FastAPI startup의 백그라운드 루프가 미완 잡을 스캔해 이어받는다. 메모리에 상태를 남기지 않는다.
