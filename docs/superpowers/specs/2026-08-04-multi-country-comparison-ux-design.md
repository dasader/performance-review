# 다국가 비교 보고서와 진입 경로 설계 (2026-08-04)

## 1. 무엇이 문제인가

5단계로 국가 비교 보고서를 만들었지만 **쓸 수 있는 상태가 아니다.**

| 증상 | 실태 |
|---|---|
| 비교 보고서에 들어갈 방법이 없다 | 주소를 직접 입력해야 한다 |
| 타국 보고서로 갈 방법이 없다 | `?country=CN`을 손으로 붙여야 한다 |
| 무엇이 생성돼 있는지 모른다 | 관리자 격자에 국가 축이 없다 |
| 다건 생성에 손이 많이 간다 | 비교는 한 건씩만 큐잉된다 |

**세부기술 분석의 일괄 생성은 이미 있다** — `_queue_all_active`가 `schedule_settings.countries`를
순회하므로, `KR,US,CN`을 넣고 "지금 실행"을 누르면 55 × 2연도 × 3국이 한 번에 큐잉된다.
현재 `KR`만 설정돼 있어 안 쓰이고 있을 뿐이다. **이 부분은 새로 만들지 않는다.**

## 2. 핵심 결정 — 다국가 보고서에서 국가별 내용이 축약되지 않아야 한다

사용자 요구: 여러 나라를 한 보고서에 담되 **각국의 개별 비교 내용이 축약되지 않을 것.**

이는 이 프로젝트가 반복해 부딪힌 압축 문제와 같은 성격이다(§6 "이중 압축", 성과유형
9개 중 3개만 서술). 그리고 **프롬프트로 분량을 지시하는 방식은 실측으로 반복 실패했다** —
2026-08-04 하루에만 두 번(대조표 형식 변형 → 대조표 통째 생략).

그래서 프롬프트가 아니라 **구조로 막는다.**

### 채택 — 쌍별 생성 후 종합

```
KR,US,CN,JP 비교 요청
  ├ KR vs US  → 쌍별 보고서 ┐
  ├ KR vs CN  → 쌍별 보고서 ├→ sections_json에 보관(버리지 않는다)
  ├ KR vs JP  → 쌍별 보고서 ┘
  └ 종합 1콜(쌍별 결과를 입력으로) → report_md
```

**이 코드베이스가 같은 문제를 이미 이 방법으로 풀었다.** 논문 500건이 넘으면 성과유형별로
나눠 만든 뒤 종합하고, 중간 보고서를 `analyses.sections_json`에 남긴다(2단계). 참고문헌이
14 → 134개가 된 것이 그 효과였다. 새로 발명할 구조가 아니다.

국가가 늘어도 각 쌍의 분량은 그대로다 — **구조적으로 축약이 불가능하다.**

**2개국이면 종합을 건너뛴다.** 쌍이 하나뿐이라 그것이 곧 보고서다. 현행 동작과 콜 수가
그대로 유지된다.

### 기각한 대안

| 안 | 기각 이유 |
|---|---|
| 성과유형별 소절 강제(1콜 유지) | 한 콜 안에서 분량이 경쟁하는 구조는 그대로다. 4개국이면 다시 눌린다 |
| 국가별 절을 요구 | 비교가 아니라 나열이 된다. 주제별로 묶어야 대조가 성립한다 |

## 3. 실측 — 토큰·비용·시간

`gemini-3.1-flash-lite`, 차세대 메모리반도체 2025 실제 데이터로 `count_tokens` 측정.

| 구성요소 | 토큰 |
|---|---:|
| `COMPARE_INSTRUCTION` | 1,435 |
| 대조표 (2개국 / 4개국) | 390 / ~570 |
| 국가별 종합 보고서 1건 | ~2,150 |
| 비교 보고서 출력 1건 | ~2,100 |

**한국 + 미·중·일(4개국) 1건**

| 호출 | 입력 | 출력 |
|---|---:|---:|
| KR vs US | ~6,100 | ~2,100 |
| KR vs CN | ~6,100 | ~2,100 |
| KR vs JP | ~6,100 | ~2,100 |
| 종합 | ~8,300 | ~2,000 |
| **합계 (4콜)** | **~26,600** | **~8,300** |

**약 $0.01/건.** 세부기술 보고서 하나 만드는 비용($0.0105)과 같은 수준이다.
55개 세부기술 × 2개년 전부면 110건 ≈ **$1.1**.

thinking=high라 출력에 사고 과정이 더 붙어 실제 비용은 이보다 조금 높을 수 있다.

## 4. 잡 루프 — 한 틱에 비교 하나(쌍별 포함) 전체

**문제**: 현행 `advance_field_reports`는 한 틱(30초)에 보고서 하나를 처리한다. 4콜짜리
비교를 콜 단위로 쪼개면 1건에 2분, 110건이면 55시간이라 일괄이 성립하지 않는다.

**결정**: **한 비교 = 한 틱**. 쌍별 3콜 + 종합 1콜을 한 틱 안에서 순차 처리한다.
110건이면 약 55분으로 실용 범위에 든다.

**"한 틱에 하나"의 취지를 깨지 않는다** — 그 규칙은 API가 동시에 얻어맞지 않게 하려는
것인데, 쌍별 콜은 순차라 동시성이 늘지 않는다. 틱 하나가 최대 2분간 블로킹되지만
로드맵 점검이 이미 17초 걸리므로 성격이 같다.

### 함께 고칠 것 — 보고서 처리를 분석 루프 뒤로 옮긴다

확인 결과 **영향이 있다.** `loop()`는 `advance_field_reports(db)`를 **분석 루프보다 먼저**
부른다. 2분짜리 비교가 그 틱의 세부기술 분석 진행을 통째로 2분 늦춘다.

```python
run_scheduled_if_due(db)
resume_paused(db)
await advance_field_reports(db)   # ← 여기서 최대 2분 블로킹
for analysis in active:           #    분석은 그동안 멈춰 있다
    await advance(db, analysis)
```

**`advance_field_reports`를 분석 루프 뒤로 옮긴다.** 한 줄 이동이고 잃는 것이 없다 —
보고서 합성은 파이프라인(검색·추출)보다 우선순위가 낮고, 지금 순서가 앞인 데에는
근거가 없다(주석은 `advance_field_reports` **안에서의** 종합/점검 순서만 설명한다).

이 이동이 없으면 월간 실행 중에 비교를 큐잉했을 때 분석 전체가 매 틱 2분씩 밀린다.
겹치는 경우가 드물기는 하다 — 비교는 대상 국가가 모두 `done`이어야 큐잉되므로 —
그러나 이미 끝난 세부기술의 비교를 돌리면서 다른 세부기술이 진행 중인 상황은 실제로 생긴다.

## 5. 데이터 모델 — 마이그레이션 0019

`country_comparisons`에 컬럼 하나를 더한다.

```
sections_json  JSON  NOT NULL DEFAULT '[]'
```

`analyses.sections_json`과 **같은 모양**이다: `[{"name": "한국 vs 미국", "body": "..."}, ...]`.
화면도 같은 펼침 패턴을 쓴다(`?withSections=1`).

재생성 시 `sections_json`을 건드리는 규칙도 `analyses`와 같다 — 처리가 끝날 때 통째로
교체하고, 실패하면 이전 것을 남긴다.

## 6. 공개 화면 — 진입 경로

### 6-1. 세부기술 보고서 상단에 국가 줄

지금 연도 이동 버튼이 있는 자리에 나란히 놓는다.

```
← 반도체·디스플레이    [한국] 미국 · 중국    |    비교: 미국 · 중국 · 전체
```

- **분석이 없는 국가는 아예 숨긴다**(비활성 표시가 아니라 미표시). 공개 화면의 방문자에게
  "미국은 아직 안 돌렸다"는 운영 사정을 보일 이유가 없다 — 그 정보가 필요한 사람은
  관리자이고, 관리자 격자(§7)가 그것을 전부 보여준다.
- 같은 이유로 **고를 것이 없으면 줄 자체를 숨긴다**(한국뿐이고 비교도 없는 경우).
- 비교 링크도 그 조합의 보고서가 실제로 있을 때만 나타난다.
- 연도를 옮길 때 국가를 유지하는 기존 규칙(`countryQuery()`)을 그대로 따른다.

필요한 API: 이 세부기술·연도에 **어떤 국가 분석과 어떤 비교가 있는지**.
`GET /api/subfields/{id}/availability?year=` 하나로 준다.

### 6-2. 분야 상세의 세부기술 표에 보고서 열

목록에서 바로 들어갈 수 있게 한다.

```
세부기술            논문    보고서
차세대 메모리        278    [KR] [US] [CN]  [비교]
반도체 첨단패키징     412    [KR]
```

`GET /api/fields/{id}/summary`가 이미 세부기술별 행을 주므로 국가 목록만 더한다.

## 7. 관리자 — 현황 격자와 일괄 생성

**새 탭을 만들지 않는다.** 기존 "분석 실행·상태" 격자에 국가 축을 더한다.

```
연도 [2026 ▾]                                    [비교 일괄 생성]

세부기술            KR   US   CN    vsUS  vsCN  다국
차세대 메모리        ●    ●    ●      ○     ●     ○
반도체 첨단패키징     ●    ○    ○      —     —     —
6G                  ●    ○    ○      —     —     —
```

`●` 완료 · `○` 없음 · `—` 상대국 분석이 없어 불가

- 국가 열은 `schedule_settings.countries`에 설정된 국가만 보여준다 — 안 쓰는 나라
  열이 늘어붙지 않게.
- **`다국` 열은 "설정된 국가 전체를 한 보고서로"를 뜻한다**(예: `countries=KR,US,CN`이면
  `KR,US,CN` 조합 하나). 설정이 2개국이면 1:1과 같아지므로 이 열을 숨긴다.
- **일괄 생성은 기존 `field-reports/run-all`과 같은 규약**: 대상이 안 되는 세부기술
  (상대국 분석 없음)은 조용히 건너뛰고 건수를 돌려준다.
- 스케줄 카드에 **"세부기술 분석의 국가별 일괄 실행은 여기 `countries`로 한다"**는
  안내를 둔다. 이미 되는 것을 모르고 다른 곳을 찾게 되어 있는 것이 지금 문제다.

## 8. 검증 계획

**구조가 실제로 축약을 막는지는 실행해야 안다.** 프롬프트 지시가 오늘만 두 번 실패했다.

차세대 메모리반도체 2025를 **KR+CN(2개국)** 과 **KR+US+CN(3개국)** 으로 각각 만들어 비교한다.

| 확인 | 통과 기준 |
|---|---|
| **쌍별 분량 유지** | 3개국의 `KR vs CN` 쌍별 보고서가 2개국 때 본문(~3,500자)과 비슷하다. 눈에 띄게 짧으면 구조가 안 듣는 것이다 |
| 종합이 반복하지 않는가 | 종합이 쌍별 내용을 다시 쓰지 않고 국가를 가로지르는 관찰에 집중한다 |
| 2개국 경로 불변 | 종합을 건너뛰고 1콜로 끝난다 |
| 대조표 | 코드가 넣은 표가 그대로 있다(`_with_table`) |
| 소요 | 1건 2분 이내 |

## 9. 다루지 않는 것

- **세부기술 분석의 일괄 생성** — 이미 있다(§1). 안내 문구만 더한다.
- **분야 단위 비교** — 세부기술 비교가 쌓인 뒤에 얹는다.
- **비교 조합의 자유 편집 UI** — 격자는 1:1과 `다국`(설정된 국가 전체)만 보여준다.
  그 밖의 임의 조합(예: `US,CN`처럼 한국이 빠진 조합)은 관리자 패널의 기존 콤마
  입력으로 계속 만들 수 있고, 격자에는 나타나지 않는다.
### JP는 이 작업에 포함한다 — 단, 실행은 별도 승인

`schedule_settings.countries`를 `KR,US,CN,JP`로 바꾸고 "지금 실행"으로 큐잉한다.

**비용이 작지 않다.** JP는 KR의 약 0.87배 규모로 추정되므로(6개 세부기술 표본):

| 항목 | 추정 |
|---|---:|
| 검색(OpenAlex) | ~$0.5 |
| 추출(Gemini map, 약 24,000건) | ~$6.5 |
| 보고서 110건 | ~$1.2 |
| **합계** | **~$8** |

추정의 근거는 표본 6개이므로 실제와 다를 수 있다(§9 미검증 항목). **코드 변경과 분리해
마지막 태스크로 두고, 실행 직전에 승인을 받는다** — 재추출 때와 같은 취급이다.

JP는 국제공동연구 비율이 높아(실측: 일본 논문의 47%가 자국 비주도) 귀속 4분류가 특히
의미 있는 대상이다.

US도 아직 분석이 없다. 같은 실행에 포함된다(US ≈ 1.9×KR로 추정되어 비용은 더 크다).
