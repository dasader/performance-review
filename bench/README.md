# bench — 추출(map) 단계 제공자 비교

운영 코드는 하나도 건드리지 않는다. `bench/`는 "Gemini 말고 다른 것으로 추출하면
어떻게 되는가"를 **같은 프롬프트·같은 논문**으로 재는 도구다.

```bash
# 1) Gemini 자기 일치율(기준선) — 다른 모델 결과를 읽으려면 이게 먼저다
zcat ~/perfrev-extractions-2026-08-25.sql.gz \
  | docker exec -i performance-review-db-1 psql -U perfrev -d perfrev_base
PYTHONPATH=backend:bench backend/.venv/bin/python bench/gemini_selfagreement_baseline.py

# 2) 모델 하나 측정 (.env의 OLLAMA_API_KEY 필요)
PYTHONPATH=backend backend/.venv/bin/python bench/ollama_extraction_bench.py \
    --n 60 --model glm-5.2 --out bench/results/glm-5.2-2026-08-25.json

# 3) results/*.json을 한 표로
PYTHONPATH=backend backend/.venv/bin/python bench/compare_results.py
```

**모델을 여러 개 돌릴 때는 반드시 순차로.** 계정 동시 한도(3)를 같은 키의 다른 서비스와
나눠 쓰므로 `OLLAMA_CONCURRENCY=2`로 두고, 두 모델을 동시에 띄우면 합이 4가 된다.

## 왜 기준선이 먼저인가

LLM 추출은 비결정적이다. 같은 모델·같은 프롬프트·같은 초록으로도 매번 다른 문장이
나온다. 그래서 **"Ollama가 Gemini와 요약 유사도 0.21"은 그 자체로는 아무 뜻이 없다** —
Gemini끼리가 0.385라는 것을 알아야 읽을 수 있다.

기준선 표본은 마이그레이션 `0021` **이전**의 `paper_extractions`다. 그때는 캐시 키에
`subfield_id`가 있어 같은 논문이 세부기술마다 따로 추출됐고(19,904그룹), 그 형제 행이
곧 "같은 입력을 두 번 돌린 결과"다. `0021`이 그 중복을 지웠으므로 **운영 DB로는 더
이상 잴 수 없다** — 배포 전 백업이 있어야 한다.

| Gemini 자기 일치 (19,904쌍) | |
|---|---|
| 성과유형 일치 | **0.830** |
| 수치유무 일치 | **0.976** |
| 수치 자카드 | **0.681** |
| 요약 유사도(문자 바이그램) | **0.385** |

### 자기 일치 — 제공자 비교의 올바른 지표 (2026-08-26)

**"vs Gemini 일치"는 품질이 아니라 교체 가능성이다.** Gemini는 정답이 아니고, 정답 라벨은
존재하지 않는다. 두 모델의 라벨 분포가 같으면 교차 일치는 Gemini 자기 일치(0.830)와
같아지므로, 교차 0.56은 "분포가 다르다"까지만 말하고 "더 나쁘다"는 말하지 않는다.
항상 아키텍처를 알고리즘이라 부르는 모델은 자기 자신과 100% 일관되면서도 교차 일치가
낮다 — 그건 노이즈가 아니라 다른 분류 체계다.

그래서 후보 모델을 **같은 논문에 두 번** 돌려 자기 일치를 잰다(`ollama_selfagreement.py`).

```bash
PYTHONPATH=backend:bench backend/.venv/bin/python bench/ollama_selfagreement.py \
    --model deepseek-v4-pro:0813 --n 200 --think none --temperature 1.0
PYTHONPATH=backend:bench backend/.venv/bin/python bench/selfagreement_table.py
```

| 모델 | temperature | 자기 일치 | 95% CI | 유효 쌍 |
|---|---|---|---|---|
| **gemini-3.1-flash-lite** | **0.0** | **1.000** | [0.981, 1.0] | 200/200 |
| deepseek-v4-pro:0813 | 기본 | 0.930 | [0.886, 0.958] | 200/200 |
| deepseek-v4-pro:0813 | 0.0 | 0.925 | [0.880, 0.954] | 200/200 |
| deepseek-v4-pro:0813 | 1.0 | 0.895 | [0.845, 0.930] | 200/200 |
| gemini-3.1-flash-lite | 1.0 | 0.815 | [0.755, 0.863] | 163/200 |
| minimax-m3 | 기본 | 0.810 | [0.691, 0.891] | **58/200** |
| glm-5.2 | 기본 | 0.804 | [0.730, 0.862] | 138/200 |
| deepseek-v4-flash:0731 | 기본 | 0.787 | [0.722, 0.840] | 183/200 |

세 가지가 나왔다.

**1. Gemini의 17% 불일치는 전부 temperature 탓이다.** 0.0에서 200/200 완전 일치.
운영이 temperature를 지정하지 않아 API 기본값 1.0으로 돌고 있었고, 1.0 실측(0.815)이
전수 기준선(0.830)과 맞는다 — 측정 장치가 옳다는 검증이기도 하다.

**2. 같은 조건이 Ollama에는 통하지 않는다.** pro:0813은 temperature 0.0에서도 0.925다.
서빙 단 비결정성(MoE 라우팅, 배치 커널의 부동소수점 비결합성)으로 보이며, 이 바닥은
**제공자마다 다르지 보편적이지 않다.**

**3. 그래서 자기 일치만 놓고 보면 Gemini(temp 0)가 모든 후보를 이긴다.** 다만 기본값
그대로 비교하면 pro:0813(0.930)이 Gemini(0.815)를 앞선다 — **어느 쪽 결론을 말하는지는
temperature를 명시했느냐에 달려 있다.** 두 스크립트에 `--temperature`를 붙인 이유다.

`--temperature`를 생략하면 제공자 기본값(Gemini 1.0 / Ollama 서버 0.8)으로 도는데,
그 상태의 모델 간 비교는 기본값 차이에 오염되어 있다. **비교할 때는 반드시 명시할 것.**

#### 표본과 탈락

`fetch_papers`는 `ORDER BY md5(paper_key) LIMIT n`이라 **모든 모델이 같은 논문을 받는다**
(n=60은 n=200의 앞 60건). 다만 **분석에 들어가는 표본은 모델마다 다르다** — 파싱 실패
(JSON 아님 또는 필수 5개 키 누락)한 응답이 빠지고, 자기 일치는 두 회차 모두 성공해야
세므로 탈락이 두 번 걸린다. minimax는 200건 중 58쌍만 남았다.

탈락이 **논문 고유가 아니라 무작위**라는 것은 확인했다 — glm의 양쪽 회차 동시 탈락은
9건으로 독립 가정 기대치 6.3과 거의 같다. 즉 "어려운 논문이 빠져 표본이 쉬워지는"
편향은 작고, 값 자체는 신뢰할 수 있다. 그래도 서로 다른 부분집합에서 잰 값이라
**모델 간 직접 비교는 짝지은 비교가 아니다.**

원시 데이터: `results/selfagreement-*.json`, `results/gemini-selfagreement-t*.json`.

자기 일치 1.000은 **재현성**이지 품질이 아니다. 추출물의 4/5는 자유 서술과 수치
목록이고, greedy 디코딩은 긴 서술에서 반복·퇴화를 일으키는 것으로 알려져 있다.
같은 논문 60건에 세 조건을 돌려 모든 필드를 비교했다(`temp0_fulltext.py`).

**퇴화는 없다.** 3-gram 반복률이 평균도 최대도 0이다. 근거율·지표 건수도 같고,

(기타↔이론/해석, 공정↔기타, 기타↔신소재)이다. temperature 1.0의 17% 샘플링 잡음과
같은 크기이며, **temp 0은 그 분포의 최빈값을 고르는 것**이다.

#### 표본 확장 — n=400 (2026-08-26)

`fetch_papers`가 `md5` 순 결정론이라 **n=400은 앞의 60건을 그대로 포함**한다.
같은 논문에 표본만 넓힌 것이므로 이전 수치와 직접 이어진다.

| 지표 | gemini t=1.0 | **gemini t=0.0** | pro:0813 t=0.0 |
|---|---|---|---|
| 요약 길이 평균 | 114 | 110 | 139 |
| 요약 3-gram 반복률 (평균/**최대**) | 0.0 / **0.064** | 0.0 / **0.045** | 0.001 / 0.088 |
| approach 채움 | 395/400 | **397/400** | 380/400 |
| improvement 채움 | 309/400 | 306/400 | 285/400 |
| metrics 건수 평균 | 1.31 | 1.29 | 1.33 |
| 수치 근거율 | 0.968 | 0.970 | 0.968 |
| **빈 값 행** | **23** | **18** | **94** |
| └ **누락**(동료가 같은 지표를 채움, **하한**) | **0** | **0** | **28** |
| └ 정당/미상 | 23 | 18 | 66 |
| └ 누락이 걸린 논문 | 0 | 0 | **14** |
| 지수 붙은 지표 → 보존 | 3/5 | 3/5 | **5/5** |

**퇴화는 n=400에서도 없다.** 반복률 평균이 0이고, 최대값은 t=0.0(0.045)이 t=1.0(0.064)
보다 **낮다.** greedy가 반복을 늘린다는 우려의 반대 방향이다.

**해석 유지도 확인된다.** 요약 유사도 t0↔t1 **0.426**은 Gemini 자기 유사도 기준선
0.385보다 여전히 높고, `achievement_type`은 336/400(84%) 일치한다 — temperature 1.0의
17% 잡음과 같은 크기다.

**pro:0813의 수치 누락은 규모에서 더 뚜렷해졌다.** 빈 값 94개 중 **28개가 누락**이고
14개 논문에 걸쳐 있다. Gemini는 양쪽 temperature에서 **0개**다. 초록에 `94.2%`·
`98.13%`·`97%` 등이 명시돼 있고 Gemini가 그 값을 채운 자리에서 pro:0813은 지표 이름과
단위까지 맞게 뽑고 값만 비웠다. **metrics 추출이 이 파이프라인의 존재 이유 중 하나이므로
제공자 판단에서 재현성 다음가는 결격 사유다.**

#### 빈 행 판정은 행 단위여야 한다 (방법 정정)

처음에는 **논문 단위**로 판정했다 — "초록에 단위 붙은 수치가 있으면 그 논문의 빈 행은
전부 누락". 양방향으로 틀린다.

- **과대**: 초록이 정확도 98%만 말하고 지연시간은 말하지 않는데 모델이 두 행을 만들면
  지연시간의 빈 값까지 누락으로 세어진다.
- **과소**: `5,673`(쉼표)이나 단위 없는 숫자를 정규식이 못 잡아 "수치 없음"으로 보고
  정당으로 넣는다 — 실측 최소 7건.

행 단위로 물으려면 "*이 지표*의 값이 초록에 있었는가"를 알아야 하는데, 초록은 영문이고
지표명은 국문 번역이라 키워드 매칭이 성립하지 않는다. 그래서 **동료 모델을 신탁으로
쓴다**(`blank_metric_audit.py`): 같은 논문에서 다른 모델이 같은 지표를 근거 있는 값으로
채웠다면 그 수치는 초록에 있었던 것이다. 지표명은 셋 다 국문이라 비교가 성립한다.

이 판정은 **누락의 하한**이다 — 두 모델이 함께 놓친 수치는 잡히지 않는다. 과대
계상하지 않으므로 "적어도 이만큼"으로 읽는다. 논문 단위 판정이 주던 40건은 이 방법에서
**28건**이 되고, Gemini의 1건은 0건이 된다.

빈 행 수 차이(23·18·94) 자체는 **누락이 아니라 관습 차이가 주된 원인**이다. 초록에
단위 붙은 수치가 없는 논문 255건에서 논문당 빈 행 수는 세 조건 모두 2.0~2.2로 같고,
**행을 만드는 논문 수만 다르다**(Gemini 8개 대 pro:0813 24개). Gemini는 값이 없으면
`metrics: []`로 두고, pro:0813은 지표 이름만 있는 빈 행을 만든다.

지수 보존은 pro:0813이 5/5, Gemini가 3/5로 방향이 유지되지만 **표본이 5개뿐**이라
아직 주장할 수 없다.

#### 빈 지표 행 — 두 종류가 섞여 있다 (n=60 최초 관찰)

값에 숫자가 없는 `metrics` 행이 deepseek 10개 / Gemini 5개로 두 배였다. 처음에는
이를 "정성 값이 많다 = 지표로서 쓸모가 떨어진다"로 적었으나 **원문 대조 결과 틀렸다.**

빈 값이 나온 논문은 전부 **4건**뿐이고, **Gemini의 2건은 deepseek의 4건에 포함된다**
(부분집합). 그 4건이 두 종류로 갈린다.

| 논문 | 초록의 수치 | gemini t=0.0 | pro:0813 t=0.0 |
|---|---|---|---|
| CRISPR 유채 라이브러리 | **94.2% · 68.4%** | 둘 다 추출 | 이름만, 값 `None` |
| Bayan Obo 광미 | **7% · 0.138% · 22.28%** | 셋 다 추출 | 이름만, 값 `None` |
| GLAD (OOS 의도 탐지) | 없음 | `'최고 수준'` | `''` |
| Textual overlap (번역 평가) | 없음 | `'상세 수치 미제시'` ×4 | `None` ×4 |

**아래 둘은 정당한 빈 값이다.** 초록이 지표 이름(F1-OPEN, BLEU, ROUGE-L, METEOR,
BERTScore)만 말하고 값을 주지 않는다. 세 조건 모두 같은 행 수를 만들었고, 차이는
"없음"을 어떻게 적느냐뿐이다.

**위 둘은 진짜 누락이다.** 초록에 `94.2%`·`68.4%`·`7%`·`0.138%`·`22.28%`가 그대로
적혀 있는데 pro:0813은 지표 이름과 단위(`%`)까지 맞게 뽑고도 **값만 비웠다.**
Gemini는 양쪽 temperature에서 전부 채웠다.

따라서 "두 배"는 표기 습관의 차이가 아니라 **명시된 수치 5개를 놓친 결과**다.
metrics 추출이 이 파이프라인의 존재 이유 중 하나이므로 가벼운 결함이 아니다.

역으로 Gemini t=0.0의 `'상세 수치 미제시'`는 값 없음을 명시한 것이라 빈 문자열보다
정직하지만, 값 필드에 산문을 넣는 것이라 화면에서 지표처럼 보인다.

#### 참고 — `이론/해석` 쏠림은 결함이 아니다 (정정)

pro:0813이 `이론/해석`에 32%를 몰아넣는 것을 처음에는 결함으로 적었으나, 분포
엔트로피는 **2.43bit로 Gemini t=0.0(2.44bit)과 사실상 같다**(9종 최대 3.17). 고르게
나누는 정도가 동일하고 최다 범주만 다르다 — 위 "교차 일치는 품질 지표가 아니다"와
같은 이유로 **다른 라벨링이지 나쁜 라벨링이 아니다.**

#### 부수 발견 — 근거율 검사가 지수 손실을 통과시킨다

SR 12 c 논문(HST/WFC3)에서 원문 `1.65 ± 0.19 × 10⁻⁵ L☉` · `8 ± 2 × 10⁻¹² M☉/yr`을
**Gemini가 양쪽 temperature 모두 `1.65 L☉` · `8 M☉/yr`로** 뽑았다(5·12자릿수 오차).
pro:0813만 `1.65e-5` · `8e-12`로 보존했다.

"수치 근거율 0.985"는 이것을 잡지 못한다 — `8`이 초록에 있으므로 근거 있음으로 세어진다.
**기계적 근거 검사는 존재만 보고 크기를 보지 않는다.**

운영 DB 전수로 다시 쟀다(`metric_exponent_check.py`): 원문에 `×10ⁿ`이 붙어 있던 지표
**1,883개 중 1,769개(93.9%) 보존**. 손실 114개는 상한이다(같은 숫자가 초록 다른 자리에
나오면 오탐). 즉 SR 12 c는 나머지 6%에 속한 사례이고 **계통적 결함은 아니다.**
다만 `stats.aggregate_metrics`가 이 값을 그대로 집계하므로 분포에 이상치로 남는다.

### 비용 구조가 처방을 바꾼다 — think 대 다회 추출 (2026-08-27)

**Ollama Cloud는 월 구독이라 재추출의 한계비용이 0이다.** Gemini는 batch 실측
$0.000393/건이라 현재 v3 추출분 172,220건을 다시 돌리면 **$67.6**이고 2패스면 $135다.
이 비대칭이 "무엇을 처방으로 쓸 수 있는가"를 바꾼다 — 아래 두 실험은 그 확인이다.

출발점: pro:0813은 초록에 명시된 수치를 비운다. 지표 **이름과 단위는 맞게** 뽑고
값만 비우므로 "무엇을 재야 하는지는 아는데 읽어오지 않는" 모양이다.

#### 처방 1 — 사고수준을 올린다 (n=200)

| 조건 | 값 채운 행 | 빈 행 | 누락 | 누락률 | 논문/분 | 17.2만 환산 |
|---|---|---|---|---|---|---|
| gemini t=0.0 | 257 | 12 | 0 | 0.0% | — | — |
| **think=none** | 242 | 29 | 5 | **1.8%** | **47.3** | **2.5일** |
| think=low | 263 | 25 | 18 | 6.2% | 11.1 | 10.8일 |
| think=high | **267** | 31 | 20 | 6.7% | 8.2 | 14.6일 |

**실패다.** think은 "더 많이 재려 한다"를 사고(논문당 지표 1.35 → 1.50개, 값 채운 행은
Gemini의 257도 넘는 267) "읽어온 것을 채워 넣는다"를 사지 못했다 — 누락률이 3.7배
나빠지고 속도는 5.8배 느려진다.

#### 처방 2 — 같은 논문을 여러 번 뽑아 합친다 (n=200, 3패스)

성립 조건은 **누락이 확률적인가**다. pro:0813은 temperature 0에서도 자기 일치가
0.925라 서빙 단 비결정성이 남아 있고, 실측으로 개별 패스의 누락이 10·7·8건인데
서로 다른 지표를 놓쳤다.

| 조건 | 회수율(이름) | **회수율(이름+값)** | 누락 |
|---|---|---|---|
| 1패스 | 0.638 | 0.610 | 10 |
| 2패스 | 0.657 | 0.622 | 7 |
| **합집합 1~2** | 0.720 | **0.693** | 2 |
| 합집합 1~3 | 0.728 | 0.701 | 0 |
| 신탁(gemini t=0.0) | 1.000 | 1.000 | 0 |

**성공이지만 한계가 뚜렷하다.** 1패스 0.610 → 2패스 합집합 **0.693**(+8%p)인데
3패스는 +0.8%p뿐이다. **2패스가 실용적 정답**이고, 그래도 Gemini의 1.000에는
30%p 못 미친다 — 반복해도 회수되지 않는 체계적 누락이 남는다.

#### 병합은 유사도가 아니라 정확 일치로 (실패에서 배운 것)

처음에는 지표명 유사도로 병합했다. 이름만 보는 회수율은 0.701로 좋아 보였는데
**값까지 보면 0.520으로 개별 패스(0.622)보다 나빴다** — `평문 모델 정확도`와
`암호문 추론 정확도`를 한 행으로 접으면서 살아남은 값이 엉뚱한 지표에 붙었다.

정규화한 (이름, 단위, 값)의 **정확 일치**로 바꾸니 0.693이 됐다. 유사도는
**신탁과 대조할 때만** 쓴다 — 그쪽은 번역 표기가 갈리는 서로 다른 모델의 출력을
맞추는 일이라 성격이 반대다.

> **교훈**: 이름만 보는 회수율은 병합이 지표를 뭉갤 때 **오히려 오른다**(한 행이
> 여러 신탁 지표의 이름에 걸리므로). 값까지 보는 지표가 없었으면 잘못된 병합을
> 개선으로 착각했을 것이다.

#### 비용편익 종합

| | 비용 | 소요 | 재현성 | 수치 회수율 | 판정 |
|---|---|---|---|---|---|
| **Gemini t=0.0** (현행 모델) | **$67.6** | 5.5일 | **1.000** | **1.000**(기준) | 품질 최고 |
| pro:0813 none 1패스 | **$0** | 2.5일 | 0.925 | 0.610 | 가장 빠름 |
| **pro:0813 none 2패스** | **$0** | **5.1일** | 0.925 | **0.693** | **구독 최적** |
| pro:0813 none 3패스 | $0 | 7.6일 | 0.925 | 0.701 | 한계효용 소진 |
| pro:0813 think=high | $0 | 14.6일 | — | — | **기각**(누락률 3.7배) |

**$67.6을 아끼는 대가는 수치 회수율 30%p와 재현성 0.075다.** `metrics`가
`stats.aggregate_metrics`의 입력이자 보고서의 근거 수치이므로 이 손실은 화면에
그대로 드러난다 — 교체를 권하지 않는다.

**다만 비용 구조가 바꾸는 것이 하나 더 있다: 실험의 가격.** 프롬프트 개선(C안)을
지금은 표본 n=1,200으로만 검증하고 채택에 $67.6을 걸어야 하는데, 구독 제공자에서는
**전량으로 검증하고 마음에 안 들면 되돌릴 수 있다.** 추출 품질이 아니라 *실험 환경*
으로서의 가치는 이 측정과 별개로 남는다.

### 형식 신뢰성

Gemini의 `response_schema`는 API가 디코딩 단계에서 **강제**하는 계약이지만, Ollama의
`format`은 프롬프트에 얹는 **요청**이다. 그 차이가 그대로 나온다.

| | 껍데기 없이 순수 JSON | 코드펜스로 감쌈 | 스키마 준수(벗긴 후) | metrics 타입위반 논문 |
|---|---|---|---|---|
| Gemini | 강제 | 0 | — | **0 / 263,782 원소** |
| flash · none | 7/60 | 50/60 | 57/60 | 16/57 |
| flash · low | 47/60 | 9/60 | 56/60 | 16/56 |
| **pro · none** | **58/60** | **2/60** | **60/60** | **6/60** |
| pro · low | 59/60 | 1/60 | 60/60 | 16/60 |
| glm · none | 0/60 | 57/60 | 57/60 | 22/57 |
| glm · low | 0/60 | 54/60 | 54/60 | 18/54 |
| gemma4 · none | 0/60 | 60/60 | **60/60** | 7/60 |
| gemma4 · low | 0/60 | 60/60 | **60/60** | 8/60 |

**pro가 압도적으로 낫다.** glm과 gemma4는 사실상 **항상** 감싸는데, 역설적으로 그 편이
다루기 쉽다 — 들쭉날쭉한 flash(50/60)와 달리 규칙이 하나라 벗기면 끝난다. 실제로
gemma4는 껍데기를 벗기고 나면 **60/60 스키마 준수에 타입위반도 7/60**으로, pro 다음으로
깨끗하다. 즉 "코드펜스로 감싸는가"와 "내용이 스키마를 지키는가"는 별개의 축이다.

`metrics[].value`를 string으로 선언했는데 숫자로 내는 위반은 세 모델 모두 있다.
코드펜스와 달리 **파싱은 성공하므로 조용히 DB에 들어간다** — 잡기 어려운 쪽이 진짜 비용이다.

### 내용 일치 (vs Gemini, 기준선 대비)

| | 성과유형 | 수치 자카드 | 요약 유사도 | 한국어 비율 |
|---|---|---|---|---|
| **기준선(Gemini 자기 일치)** | **0.830** | **0.681** | **0.385** | 0.651 |
| flash · none | 0.544 | 0.552 | 0.213 | 0.561 |
| flash · low | 0.571 | 0.640 | 0.229 | 0.585 |
| pro · none | 0.633 | 0.605 | 0.254 | 0.629 |
| pro · low | 0.633 | 0.610 | 0.248 | 0.608 |
| **glm · none** | **0.684** | 0.636 | 0.287 | **0.649** |
| glm · low | 0.630 | 0.588 | 0.298 | 0.632 |
| gemma4 · none | 0.650 | 0.638 | **0.314** | 0.616 |

**네 모델 모두 성과유형 일치가 기준선(0.830)에 못 미친다** — 최고가 glm·none의 0.684다.
`achievement_type`은 `reducer.group_for_reduce`의 3단 reduce 분할 키이자
`stats.by_achievement_type`의 집계 축이라, 이게 달라지면 **보고서의 구조 자체가 바뀐다.**
이것이 세 모델에 공통된 근본 장벽이고, 형식 문제와 달리 코드로 덮을 수 없다.

한국어 준수는 glm·none이 0.649로 Gemini(0.651)와 사실상 동급이다. flash가 0.561로
가장 낮은데, 영문 기술용어를 그대로 두는 경향이 있다.

### 사고수준을 줄여도 되는가 — 모델마다 다르다

같은 모델에서 `low`와 `none`이 서로 얼마나 일치하는지(성과유형):

| | low↔none 성과유형 | low↔none 수치 자카드 |
|---|---|---|
| flash | 0.679 | 0.637 |
| pro | 0.750 | 0.647 |
| glm | 0.712 | 0.608 |
| **gemma4** | **0.783** | **0.754** |
| *(기준선: Gemini 자기 일치)* | *0.830* | *0.681* |

**넷 다 성과유형에서 기준선 0.830보다 낮다.** 즉 사고수준을 바꾸는 것은 "같은 결과를
더 싸게"가 아니라 **다른 결과를 얻는 것**이다. gemma4만 예외적으로 안정적이어서
(0.783 / 수치는 0.754로 기준선보다도 높다) 사고수준 선택의 영향이 가장 작다.

방향도 모델마다 반대다.

- **flash**: `none`이 형식을 무너뜨린다(코드펜스 50/60 대 9/60, 수치 자카드 0.552 대
  0.640, 가짜 빈 지표 2건). 사고가 형식을 지키게 만드는 장치에 가깝다.
- **pro**: `none`이 오히려 형식이 **더 낫다**(metrics 타입위반 6/60 대 16/60). 내용
  일치는 동일(0.633).
- **glm**: `none`이 내용 일치가 더 낫다(성과유형 0.684 대 0.630, 수치 0.636 대 0.588).
- **gemma4**: `none`이 성과유형·요약에서 낫고(0.650 대 0.600, 0.314 대 0.292) 형식은
  사실상 동일하다. 게다가 `low`가 `none`보다 **느리기만 하다**(4.8/분 대 7.7/분).

그러므로 **"사고를 켜면 안전하다"는 일반화는 성립하지 않는다.** Gemini에서
`THINKING_MAP: low → minimal`을 검토할 때 이 결과를 근거로 쓰면 안 된다 — 거기서는
형식을 `response_schema`가 강제하므로 조건이 다르다.

## 읽는 법 — 숫자가 오해를 부르는 곳

**요약 유사도 0.21~0.30은 품질이 나쁘다는 뜻이 아니다.** 샘플을 직접 보면 Ollama 쪽이
오히려 **더 구체적**이다 — 기법명(CEEMDAN, SARIMA/LSTM/BiLSTM)과 수치
(1.65×10⁻⁵ L⊙, 8×10⁻¹² M⊙/yr)를 적는 반면 Gemini는 "도출하였다"로 뭉갠다. 길이도
1.3~1.6배(170자 대 109자)다. 어휘 자카드는 "같은 얘기를 다르게 썼다"와 "다른 얘기를
했다"를 구분하지 못하므로, 이 지표만 보고 판단하면 안 된다.

**성과유형 일치율은 그렇지 않다.** enum 9종 중 하나를 고르는 분류라 표현 차이가 개입할
여지가 없고, 기준선이 0.830으로 높다. 여기서 벌어진 차이는 실제 판단 차이다.

### 불일치 3,381건의 62%가 다섯 쌍에 몰려 있다

### 원인 — enum이 서로 다른 두 축을 섞고 있다

아홉 개가 같은 질문의 답이 아니다.

- **무엇을 만들었나**: 신소자 · 신소재 · 공정 · 알고리즘 · 아키텍처 · 시스템구현
- **무엇을 밝혔나**: 이론/해석
- **결과가 어땠나**: 성능향상 ← 축이 다르다
- **나머지**: 기타

`성능향상`이 가장 불안정한 것(0.616)은 우연이 아니다. 성능을 높인 논문은 **동시에**
알고리즘이나 아키텍처를 만든 논문이라, 두 라벨이 늘 같이 맞는다. 모델은 매번 동전을
던진다. 게다가 이 축은 이미 `improvement` 필드가 담고 있다 — 같은 정보를 두 곳에서
받으면서 한 곳에서는 배타적 선택을 강요하는 셈이다.

`기타 ↔ 이론/해석`(19.7%)은 `이론/해석`의 경계가 없어서다. 리뷰·서베이·시뮬레이션
해석이 어디로 가야 하는지 프롬프트가 말하지 않는다.

`알고리즘 / 아키텍처 / 시스템구현` 삼각형(34.4%)은 **입도(granularity) 규칙이 없어서**다.
"CEEMDAN 분해 + 클러스터링 + SARIMA/LSTM 하이브리드 예측 모델"은 셋 다로 읽힌다.

### 왜 그냥 두면 안 되는가

`achievement_type`은 `reducer.group_for_reduce`의 3단 reduce 분할 키다. 그리고
**분석 332건 중 91건이 3단 reduce에 걸리며, 그 91건이 추출 15.6만 건 — 전체의 82%를
차지한다.** 즉 이 흔들림은 예외 경로가 아니라 주 경로에 있다. 재실행 때마다 논문의
17%가 다른 그룹으로 옮겨 다니고, 그룹이 바뀌면 중간 보고서(`sections_json`)의 내용과
인용이 함께 바뀐다. `stats.by_achievement_type`도 같은 값을 센다.

### 좋은 소식 — enum 도입은 실제로 먹혔다

v2 시절에는 `회로설계` · `데이터셋 구축` · `신소재/시스템구현` 같은 enum 밖 값이 17종
있었다. **v3에서는 0건이다.** 스키마의 enum이 제 일을 하고 있으므로, 남은 문제는
"모델이 아무 값이나 낸다"가 아니라 "정해진 아홉 개의 경계가 겹친다"이다.

### ⚠️ 프롬프트를 고칠 때의 함정

`mapper.model_ver()`는 `f"{gemini_model}/{thinking_map}/v{EXTRACTION_SCHEMA_VERSION}"`이라
**`MAP_INSTRUCTION` 본문은 캐시 키에 들어가지 않는다.** 지시문만 고치면 캐시가 그대로
살아 있어 **옛 규칙으로 뽑은 결과와 새 규칙으로 뽑은 결과가 한 분석 안에 섞인다.**
그리고 그 사실이 어디에도 드러나지 않는다.

- enum 자체를 바꾸면(예: `성능향상` 제거) `MAP_SCHEMA` 변경이므로
  `EXTRACTION_SCHEMA_VERSION`을 올리는 것이 기존 규약이다 → 20.7만 건 전량 재추출.
- **지시문만 고치는 경우에도 올려야 한다** — 규약이 이 경우를 다루지 않을 뿐이다.

## 프롬프트 A/B — 결정 리스트가 자기 일치율을 0.833 → 0.887로 올린다

`bench/achievement_type_ab.py`. **재는 것은 정답률이 아니라 자기 일치율이다** —
성과유형에는 정답지가 없고, 문제는 같은 논문을 두 번 돌리면 다른 값이 나온다는 것이다.
각 변형을 같은 논문에 두 번 돌려 자기 자신과의 일치를 본다.

### 결과 (gemini-3.1-flash-lite, thinking=low, 운영과 동일)

| 표본 | A 현행 | B 성능향상만 제거 | C 결정 리스트 | 짝지은 검정 (A vs C) |
|---|---|---|---|---|
| n=150 | 0.813 | 0.800 | 0.867 | — |
| n=500 | 0.846 | — | 0.888 | b=47 / c=68, p=0.062 |
| **n=1,200** | **0.833** | — | **0.887** | **b=92 / c=156, p=0.0001** |
| *(95% CI, n=1200)* | *0.811~0.853* | | *0.867~0.903* | |

**A가 전수 기준선 0.830으로 수렴한 것이 실험 장치의 검증이다** — 표본이 커질수록
0.813 → 0.846 → 0.833으로 모집단 값에 붙었다. 그러므로 C의 값도 믿을 수 있다.

효과는 **+5.4%p**, 불일치로 보면 16.7% → 11.3%로 **32% 상대 감소**.

### 짝지은 검정을 써야 한다 — 독립 CI를 겹쳐 보면 안 된다

n=500에서 A(0.812~0.875)와 C(0.857~0.913)의 신뢰구간은 겹쳤다. 그러나 그것은 "차이가
없다"가 아니라 **잘못된 자로 쟀다**는 뜻이다. 같은 논문에 두 변형을 돌렸으므로 논문
단위로 짝지어야 하고(McNemar), 그렇게 하면 같은 데이터가 p=0.062를 준다. n=1,200에서
p=0.0001로 확정됐다.

### B는 실패했다 — 효과는 전적으로 결정 리스트에서 나온다

`성능향상`을 빼기만 해서는 0.813 → 0.800으로 아무것도 개선되지 않았다. 전수 분포에서
2.3%뿐인 범주라 예상 가능한 결과다. **한 번에 둘을 바꿨다면 이 사실을 몰랐을 것이다.**

### 작동 기전 — `기타`를 목록 맨 끝으로 보낸 것

| 유형 | A | C |
|---|---|---|
| 이론/해석 | 169 | **347** |
| 기타 | 135 | **30** |
| 시스템구현 | 258 | 169 |
| 공정 | 57 | 100 |
| 성능향상 | 20 | 0 |

A의 최대 혼동 쌍이던 `기타 ↔ 이론/해석`(40건)과 `기타 ↔ 시스템구현`(28건)이 C에서
**사라졌다.** `기타`가 8번째 질문이 되면서 대등한 선택지가 아니라 진짜 잔여 범주가 됐다.

C에 남은 혼동은 `시스템구현 ↔ 알고리즘`(16) · `아키텍처 ↔ 알고리즘`(15) ·
`알고리즘 ↔ 이론/해석`(15) — 결정 리스트 4·5·6번의 경계다. 다음에 손볼 곳이 여기다.

### 일관성이 올랐다 ≠ 분류가 맞아졌다 — 그래서 눈으로 봤다

애매한 것을 한 범주에 몰아넣어도 일관성은 오른다. 그래서 유형이 옮겨간 논문을 직접
읽었다.

| 이동 | 실제 논문 |
|---|---|
| 기타 → 이론/해석 | *"**A Review of** Obstacle Avoidance Path Planning Technologies"* · *"HST/WFC3 자외선 관측과 강착 해석"* · *"Personalized nutrition… precision diets"* |
| 성능향상 → 이론/해석 | *"백신 간접 비교 연구"* — `성능향상`이 명백한 오분류였다 |

리뷰 논문과 관측·해석 연구가 쓰레기통에서 의미 있는 범주로 옮겨갔다. **쏠림이 아니라
개선이다.**

### 더 손대면 나빠진다 — D·E는 실패했다 (n=1,000)

C에 남은 혼동을 마저 잡으려고 두 처방을 더 만들어 쟀다. **둘 다 실패했다.**

| 변형 | 개입 | 자기 일치율 | 불일치 건수 | 짝지은 검정(vs C) |
|---|---|---|---|---|
| **C** | 결정 리스트 | **0.891** | **109** | 기준 |
| D | C + 각 단계에 판정 규칙 추가 | 0.863 | 137 | b=107 / c=79, **p=0.047 (유의하게 나쁨)** |
| E | C + `아키텍처`를 `알고리즘`에 흡수 | 0.883 | 117 | b=87 / c=79, p=0.587 (차이 없음) |

**D가 왜 실패했는가.** 각 단계에 붙인 괄호 규칙("알려진 물질을 새 방법으로 만든 것은
공정", "기존 구조를 조합한 것은 알고리즘")이 **새로운 판단 지점**을 만들었다. 초록만으로는
"알려진 물질인가 새 물질인가", "기존 구조인가 새 구조인가"가 결정적이지 않아 또 다른
동전 던지기가 됐다. C에 없던 혼동이 새로 생긴 것이 증거다:

| D에서 새로 생긴 혼동 | 건수 | 원인이 된 규칙 |
|---|---|---|
| 공정 ↔ 신소재 | 14 | "알려진 물질을 새 방법으로 만든 것은 3번으로" |
| 공정 ↔ 알고리즘 | 15 | 위 규칙의 파급 |
| 기타 ↔ 이론/해석 | 16 | "새 방법을 제안했다면 6번이 우선" — C가 닫았던 경계를 다시 열었다 |

분포도 크게 흔들렸다: `신소재` 104 → 61, `알고리즘` 276 → 375, `기타` 20 → 33
(C가 줄여 놓은 것을 되돌렸다).

> **결정 리스트가 작동한 것은 규칙이 많아서가 아니라 순서가 명확해서다.** 각 단계에
> 조건절을 붙이면 판단 지점이 늘어 오히려 변동이 커진다. 프롬프트 안정화에서
> "더 자세히 설명한다"는 직관은 틀렸다.

**E가 왜 실패했는가.** 범주를 없애도 혼동은 **이동할 뿐 사라지지 않았다.**
`아키텍처`를 제거하자 `알고리즘`이 276 → 402로 커졌고, 혼동은
`알고리즘 ↔ 이론/해석`(27) · `시스템구현 ↔ 알고리즘`(24)으로 재분배됐다. 총 불일치는
109 → 117로 오히려 늘었다.

> **혼동은 범주 쌍의 문제가 아니라 논문 자체가 여러 범주에 걸쳐 있다는 사실에서
> 나온다.** 범주를 지우면 그 논문들은 남은 범주 사이에서 다시 흔들린다.

### 남은 혼동은 잔여 잡음이다 — 혼동 집중도가 알려준다

| | 최대 혼동 쌍이 전체 불일치에서 | 상위 5쌍 |
|---|---|---|
| A 현행 | **19.7%** | 62.1% |
| **C** | **10%** | 45% |
| D | 15% | 62% |
| E | 23% | 68% |

A에서는 불일치가 몇 개의 구체적 경계(`기타↔이론/해석` 등)에 **몰려** 있었고, 그래서
고칠 수 있었다. C에서는 11·10·10·10·8건으로 **고르게 흩어져** 있다.

> **몰려 있는 혼동은 설계 결함이고, 평평한 혼동은 작업의 본질적 모호성이다.**
> 집중도가 낮아졌다는 것은 고칠 것을 다 고쳤다는 신호로 읽는다. D와 E가 집중도를
> 다시 높인 것(15%, 23%)은 새 결함을 만들었다는 뜻이다.

**결론: C를 채택한다. 더 손대지 않는다.**

### 채택할 때의 비용

C는 저장된 v3와 835/1,200(69.6%)만 일치한다 — **약 30%의 논문이 다른 라벨을 받는다.**
`MAP_SCHEMA`의 enum이 바뀌므로(`성능향상` 제거) `EXTRACTION_SCHEMA_VERSION` 상향이
규약이고, 20.7만 건 전량 재추출(약 $81)이 따라온다. 섞인 상태로 두면 한 분석 안에 두
분류 체계가 공존하므로 **부분 적용은 선택지가 아니다.**

## 성과유형 불일치는 모델 탓이 아니다 — 프롬프트 탓이다

`gemma4:31b`를 넣은 이유 중 하나는 가설 검증이었다. 지금까지의 공통 장벽이 성과유형
분류였으므로, **Gemini와 학습 계보가 가까운 Google 모델이라면 그 분류를 더 비슷하게
할 것인가**를 봤다.

**아니었다.** gemma4·none은 0.650으로, 중국 Zhipu의 glm-5.2·none(0.684)보다 낮다.
계보로 설명되지 않는다.

더 결정적인 것은 기준선 자체다. **Gemini는 같은 논문·같은 프롬프트로 자기 자신과도
17% 어긋난다**(0.830). 9지 택일 강제 분류에서 이 정도 자기 불일치는 모델이 흔들리는
것이 아니라 **범주 정의가 겹친다**는 뜻이다. `MAP_INSTRUCTION`의 성과유형 목록은
아홉 개를 나열할 뿐 판정 규칙도 예시도 없다 — "성능향상"과 "알고리즘",
"시스템구현"과 "아키텍처"를 가르는 기준이 없다.

그래서 이 항목은 **제공자를 바꾸든 안 바꾸든 손볼 값어치가 있다.** Gemini에 머물러도
같은 논문이 재실행마다 다른 유형으로 분류되고 있고, 그것이 3단 reduce의 그룹 분할과
`stats.by_achievement_type`을 흔든다. 다만 프롬프트를 고치면 `model_ver`가 바뀌므로
전량 재추출이 따라온다 — 별건으로 다룰 일이다.

## 결론

**네 모델 모두 지금 상태로는 교체할 수 없다.** 막는 것은 속도가 아니라 성과유형 분류가
기준선 아래로 크게 어긋난다는 것이다(0.544~0.684 대 0.830).

굳이 후보를 고르면 **glm-5.2 · think=none**이다.

- 5.0일로 Gemini Batch(5.5일)와 같은 급
- 성과유형 0.684로 넷 중 최고, 한국어 0.649로 Gemini와 동급
- 코드펜스는 100%에 가까워 규칙이 하나 — 벗기면 끝난다
- 약점: `metrics[].value` 타입위반 22/57(39%)로 넷 중 최다 — 저장 시 캐스팅 필요

나머지 셋은 각각 한 축이 뛰어나지만 다른 축에서 걸린다.

- `deepseek-v4-pro` — 형식이 가장 깨끗하다(스키마 100%, 코드펜스 2/60, 타입위반 6/60).
  그러나 13.3일로 느리고 성과유형 0.633.
- `deepseek-v4-flash` — 가장 빠르다(`none` 4.1일). 그러나 형식·내용·한국어 모두 최하.
- `gemma4:31b` — **가장 안정적이다**. 사고수준을 바꿔도 결과가 잘 흔들리지 않고
  (low↔none 성과유형 0.783, 수치 0.754 — 수치는 기준선보다도 높다), 껍데기를 벗기면
  스키마 60/60에 요약 유사도 0.314로 넷 중 최고다. 그러나 **18.6일로 가장 느리다** —
  31.3 tok/s는 flash의 1/5이다. 정확도가 우선이고 시간이 문제가 아닌 소규모 재처리에는
  이 모델이 맞다.
