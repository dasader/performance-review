# bench — 추출(map) 단계 제공자 비교

운영 코드는 하나도 건드리지 않는다. `bench/`는 "Gemini 말고 다른 것으로 추출하면
어떻게 되는가"를 **같은 프롬프트·같은 논문**으로 재는 도구다.

```bash
# 1) Gemini 자기 일치율(기준선) — 다른 모델 결과를 읽으려면 이게 먼저다
zcat ~/perfrev-extractions-2026-08-25.sql.gz \
  | docker exec -i performance-review-db-1 psql -U perfrev -d perfrev_base
PYTHONPATH=backend:bench backend/.venv/bin/python bench/gemini_selfagreement_baseline.py

# 2) Ollama Cloud 측정 (.env의 OLLAMA_* 필요)
PYTHONPATH=backend backend/.venv/bin/python bench/ollama_extraction_bench.py --n 60
```

## 왜 기준선이 먼저인가

LLM 추출은 비결정적이다. 같은 모델·같은 프롬프트·같은 초록으로도 매번 다른 문장이
나온다. 그래서 **"Ollama가 Gemini와 요약 유사도 0.21"은 그 자체로는 아무 뜻이 없다** —
Gemini끼리가 0.385라는 것을 알아야 읽을 수 있다.

기준선 표본은 마이그레이션 `0021` **이전**의 `paper_extractions`다. 그때는 캐시 키에
`subfield_id`가 있어 같은 논문이 세부기술마다 따로 추출됐고(19,904그룹), 그 형제 행이
곧 "같은 입력을 두 번 돌린 결과"다. `0021`이 그 중복을 지웠으므로 **운영 DB로는 더
이상 잴 수 없다** — 배포 전 백업이 있어야 한다.

## 읽는 법 — 숫자가 오해를 부르는 두 곳

**요약 유사도 0.21은 품질이 나쁘다는 뜻이 아니다.** 샘플을 직접 보면 Ollama 쪽이
오히려 **더 구체적**이다 — 기법명(CEEMDAN, SARIMA/LSTM/BiLSTM)과 수치
(1.65×10⁻⁵ L⊙, 8×10⁻¹² M⊙/yr)를 적는 반면 Gemini는 "도출하였다"로 뭉갠다. 길이도
1.3~1.6배다. 어휘 자카드는 "같은 얘기를 다르게 썼다"와 "다른 얘기를 했다"를 구분하지
못하므로, 이 지표만 보고 판단하면 안 된다.

**성과유형 54~57%는 진짜 문제다.** 기준선이 83%이므로 샘플링 잡음으로 설명되지 않는다.
`achievement_type`은 `reducer.group_for_reduce`의 3단 reduce 그룹 분할 키이자
`stats.by_achievement_type`의 집계 축이라, 이게 달라지면 **보고서의 구조 자체가 바뀐다.**

## 결론

**지금 상태로 교체할 수 없다. 막는 것은 속도가 아니다.**

속도는 오히려 놀랍다 — `think=none`은 동시성 2에서 49,968건/일로, 이 시스템이 Gemini
Batch로 실제 낸 최대치(37,404건/일)보다 빠르다. "Ollama는 느리다"는 통념은 적어도 이
모델·이 규모에서는 맞지 않았다. 다만 Gemini Batch 쪽 37,404는 천장이 아니라
`BATCH_MAX_CONCURRENT_JOBS=2` 설정의 결과이고, Ollama는 계정 동시 한도(3)가 천장이다.

막는 것은 둘이다.

1. **구조화 출력이 강제되지 않는다.** Gemini의 `response_schema`는 계약이지만 Ollama의
   `format`은 권고다 — `think=none`에서 60건 중 50건이 코드펜스로 감싸 왔고, 지표
   `value`를 string으로 선언했는데 28%의 논문에서 숫자로 냈다(Gemini는 263,782개 원소
   전부 string). 방어 파싱과 캐스팅으로 덮을 수는 있지만, 덮어야 한다는 사실 자체가
   비용이다.
2. **성과유형 분류가 기준선 아래로 크게 어긋난다**(54~57% vs 83%). 과거 Gemini 추출과
   섞이면 같은 세부기술 안에서 분류 체계가 두 벌이 된다.

### 사고수준을 줄여도 되는가 — 아니다

`think=none`은 3.7배 빠르고 출력 토큰이 1/4.6이지만, 줄어드는 것이 사고만이 아니다.

- 코드펜스 50/60 (low는 9/60) — 형식 준수가 같이 무너진다
- 수치 자카드 0.552 (low 0.640) — 수치 추출 품질이 떨어진다
- 가짜 빈 지표 2건, 빈 응답 1건 (low는 0건)
- `low↔none` 성과유형 일치는 67.9%로, **같은 모델인데도 서로 크게 다르다**

즉 이 모델에서 사고는 "품질을 조금 더하는 옵션"이 아니라 **형식을 지키게 만드는 장치**에
가깝다. Gemini에서 `THINKING_MAP=low → minimal`이 안전해 보였던 것(출력 −40%, 형식은
스키마가 강제)과는 상황이 다르다.

Ollama Cloud는 토큰이 아니라 **GPU 시간 기준 구독**이라 정액이다. 다만 무료/Pro 티어의
세션·주간 한도가 공개되지 않아, 20만 건 연속 처리가 한도에 걸리는지는 **미검증**이다.
직접 API로 가면 `think=low`는 현행보다 오히려 **비싸다**(출력 토큰이 3.7배).
